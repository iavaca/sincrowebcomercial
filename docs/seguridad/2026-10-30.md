# Auditoría de seguridad: bandeja (30/10/2026)

Agente: security-auditor. Código auditado: HEAD d6ec00e.

**Veredicto: aprobado para liberar.** No hay hallazgos críticos, altos ni medios. Hay dos bajos, que se arreglan después de esta auditoría.

## Modelo de amenazas
- **Actores:** cualquier persona de internet, cualquier usuario de GitHub que pase por el OAuth, un sitio malicioso abierto en el navegador de Iván (CSRF o clickjacking), y quien escribe issues o PRs (contenido no confiable).
- **Activos:** el token y el refresh token de GitHub dentro de la cookie, el poder de mergear en claude-agents, y el poder de cambiar labels, comentar y cerrar issues.
- **Límites de confianza:** navegador ↔ /api (cookie + Origin), /api ↔ GitHub (token del usuario) y contenido de GitHub ↔ HTML (escapado).

## Qué se revisó y aguanta
- **OAuth:** el state son 32 bytes al azar, va sellado con AES-GCM en una cookie de 10 minutos y se compara con largo fijo. `volver` solo acepta anclas, así que no hay redirect abierto. Un login CSRF no sirve porque solo entra el uid 100360837.
- **Cookie:** AES-256-GCM con IV al azar en cada sello. Usa AAD distinto para la sesión y para el state, así que una no abre como la otra. Tiene un máximo de 7 días que no se renueva con el refresh, y prefijo `__Host-`.
- **Autorización:** todos los endpoints verifican el uid. En `accion`, el servidor vuelve a leer en GitHub las labels, la clase y si el issue o PR sigue abierto. El merge vuelve a leer el SHA, si es mergeable y los checks, y manda el `sha` en el PUT.
- **CSRF:** las rutas que cambian cosas exigen Origin igual a APP_ORIGIN. `accion` además exige JSON. La cookie es SameSite=Strict y `frame-ancestors 'none'` evita el clickjacking.
- **XSS:** todo el contenido pasa por escaparHtml. Los links se limitan a https: y mailto:. La CSP no permite scripts inline.
- **Inyección:** las consultas GraphQL son fijas y usan variables. Los repos salen de un mapa fijo, los números se validan como enteros y los agentes salen de una lista blanca.
- **Errores y logs:** las respuestas usan textos fijos y los logs no guardan tokens ni cuerpos de GitHub.
- **Workflow:** `contents: read`, corre con `pull_request` y no usa secretos.
- **Secretos:** se revisó todo el historial y no hay ninguno.
- **Tests:** 167/167 pasan y el typecheck no da errores.

## Hallazgos
1. **[BAJO] lib/html.ts:** el texto "Abrir WhatsApp" se puede falsificar con `https://wa.me.evil.tld`. El arreglo es comparar el hostname exacto.
2. **[BAJO] api/logout.ts:** salir no revoca el token en GitHub, así que una cookie copiada sigue sirviendo hasta 7 días. El arreglo es revocar el token con DELETE /applications/{client_id}/token.

## Pruebas en vivo (producción, 30/10 19:20)
- `/api/bandeja` sin cookie → 401.
- `/api/login?volver=https://evil.com` → 302 a GitHub con el redirect_uri correcto.
- `/api/callback` con un state falso → 400.
- POST a `/api/accion` con Origin ajeno → 403.
- Los headers CSP, nosniff, no-referrer y HSTS llegan presentes.

**Nota aparte:** la acción "asignar" agrega `agente:<x>` a pedidos escritos por clientes. Si una automatización dispara un agente con esa label, el riesgo de prompt injection está en ese flujo, no en esta app.
